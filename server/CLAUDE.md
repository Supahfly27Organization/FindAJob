# server/ — FindAJob API

## Architecture
- Node.js (ESM), Express 4, SQLite via `better-sqlite3` (synchronous — no async DB calls needed for this single-user local app).
- `src/app.js` — `createApp(db)` builds the Express app (no `listen()`, so it's testable via Supertest); `errorHandler` maps thrown errors to HTTP responses.
- `src/server.js` — the real entrypoint: opens/creates the SQLite DB, builds the app, registers all routes, serves the built client from `client/dist` when present, starts listening, and opens the user's browser.
- `src/db/schema.sql` — the entire schema (two tables: `position_titles`, `postings`), applied on every startup as `CREATE TABLE IF NOT EXISTS`. A DB created before the Settings page was removed still carries an orphan `settings` table; nothing reads it and it is intentionally not dropped. No migration framework for v1 — new columns on an existing table are also added to the `CREATE TABLE` here (so a fresh DB gets them immediately) **and** to the `ADDITIVE_COLUMNS` list in `src/db/index.js` (`ALTER TABLE ... ADD COLUMN`, each wrapped to ignore "duplicate column name" so it's a no-op on a DB that already has it) — that second step is what actually updates an existing DB in place.
- `src/services/*` — business logic and all DB access (one file per domain concept).
- `src/routes/*` — thin Express routers that call into services and translate results/errors to HTTP.

## Key decisions
- `ValidationError`/`NotFoundError` (`src/errors.js`) carry `.status`; the shared `errorHandler` in `app.js` reads that to respond, so route handlers just `try { ... } catch (error) { next(error); }`.
- Deleting a position title does **not** delete its postings — `postings.position_title_id` is nullable with `ON DELETE SET NULL`; the service explicitly unlinks in a transaction so nothing on disk (adapted resumes, applied CVs, once those exist) is ever silently lost.
- **There is no Settings page, no `/api/settings/*` routes and no `settings` table** — both configurable things are files the user edits directly, and neither has a DB fallback (removed deliberately: the .env/root-file path is the only one David uses, and a second source of truth was just something to get out of sync). The OpenAI key is `OPENAI_API_KEY` in the repo-root `.env`, loaded by `dotenv` at the top of `config.js` with an explicit path so it works regardless of cwd (npm workspace scripts run with cwd `server/`), and read through `config.js`'s `getOpenAiKey()` (blank/whitespace counts as unset). Missing-config errors name the file to fix ("Set OPENAI_API_KEY in the .env file…", "Add your resume as Resume.docx…") — the UI can't fix them, so the message has to.
- `posting.status` is exactly `New | Applied | In Progress | Rejected` (a DB `CHECK` constraint enforces this); `viewed` is a separate boolean column, not a status value.
- Search (`searchService.js`) is a pure orchestrator: it validates the OpenAI key is configured, delegates the actual call to `openaiClient.js` (swappable via a `fetchPostings` param so tests never hit the network), then hands raw candidates to `postingService.saveSearchResults`, which enforces the 20-result cap, the 45-day freshness window, and URL-based dedup (existing rows/status are never touched on a re-find).
- **The search is a fan-out, not one call.** `searchJobPostings` issues one `responses.create` per entry in `config.js`'s `JOB_SEARCH_SOURCES` (AllJobs, Drushim, JobMaster, LinkedIn, Indeed, and one unfiltered "company career pages" call), concurrently via `Promise.allSettled`, then unions them. This was a deliberate fix for two clicks seconds apart returning wildly different result sets: with a single unscoped call, *which board to look at* was itself a sampled decision, and one different token there selects a completely different corpus, so the results differ in kind rather than in wording. Pinning the board per call removes that variance; unioning several calls averages out what's left. It does **not** make search deterministic — `web_search` is a live index and re-ranks on its own, so re-running will still surface different postings. Consequences to keep in mind:
  - Each source is asked for `MAX_RESULTS_PER_SOURCE` (8), while `MAX_RESULTS` (20) still caps what one search *saves* in total. The union is therefore **interleaved round-robin** (`interleave()`), not concatenated — `Promise.allSettled` resolves in *input* order, so concatenating would let AllJobs fill the entire 20-slot quota and starve every later source on every single search.
  - A source that fails is logged and skipped, so one flaky board can't kill the search. But if **every** source fails the original error is rethrown with `.status` intact — that's load-bearing, because `searchService` maps `status === 401` to "your key was rejected"; flattening the failures into an empty result would silently turn a bad API key into "no jobs found".
  - Cost/latency scale with `JOB_SEARCH_SOURCES.length`: one search click is now 6 reasoning-model calls, not 1. Trim the list to make searches cheaper and faster.
- Search request tuning lives in `config.js` and exists specifically to close the gap with what the same query returns in ChatGPT — each piece addresses a distinct cause, so don't drop one as redundant:
  - `OPENAI_SEARCH_MODEL` defaults to a **reasoning** model (`gpt-5.6-terra`) with `reasoning.effort` from `OPENAI_SEARCH_REASONING_EFFORT` (default `high`). ChatGPT's search quality comes largely from searching, reading, noticing a gap, and searching again; a non-reasoning model like `gpt-4.1` fires one query and answers. Set `OPENAI_SEARCH_REASONING_EFFORT` to `''`/`none` if you point the model back at `gpt-4.1` — non-reasoning models reject the `reasoning` param outright.
  - `user_location` (`JOB_SEARCH_LOCATION`, default IL/Tel Aviv) is sent on every call. Without it the tool retrieves unlocalized, US-skewed results — the largest single accuracy loss for an Israel-only job search, and invisible in testing because the results still *look* like job postings.
  - `tool_choice: 'required'` forces the search. With the default `'auto'` the model can decide it already knows some Israeli job boards and answer from memory — which is where fabricated URLs (the ones `isValidCandidate` exists to catch) come from.
  - `search_context_size: 'high'` (default is medium) because each result needs a description, company, location and published date extracted from the page, not just a link.
  - Output uses Structured Outputs (`text.format`, `SEARCH_RESPONSE_FORMAT`) instead of "respond with ONLY a JSON array" in prose. `strict: true` forces every property into `required`, so optional fields are modelled as `['string', 'null']` unions. `parseSearchResponse` still accepts a bare array and still strips markdown fences — that's the fallback path, not dead code, and the tests cover both shapes.
  - The adaptation call (`adaptResumeText`) was deliberately left on `gpt-4.1` + `chat.completions` — none of the above applies to it, since it does no retrieval.
- `updatePostingStatus` only accepts `New | In Progress | Rejected` — `Applied` is rejected with a `ValidationError` there and is written **only** by `appliedCvService.saveAppliedCv` (`POST /api/postings/:id/applied-cv`), so an Applied posting always has the CV she actually submitted on file. That CV lives at `APPLIED_CVS_DIR/posting-<id>.<ext>` (one per posting, overwritten on re-upload, old file deleted when the extension changes) and is written to disk *before* the DB row is touched, so a failed write leaves the status unchanged. Moving a posting *off* Applied afterwards is allowed and deliberately keeps the CV on file (the record of what was sent survives a mis-click correction). The original filename is kept in `applied_cv_original_name` purely so the download hands back the same name she uploaded.
- `posting.url` is specifically the **direct application URL** (the posting's own page — never a search-results/aggregator listing page). `buildSearchPrompt` instructs the model accordingly, but that alone isn't reliable — real test data showed ~19% of results were either a generic listing page or an outright fabricated URL (once with a Cyrillic character baked into a percent-encoded segment, once with the model's own placeholder text `"... (exact id truncated)"` saved verbatim as the URL). `isValidCandidate` in `postingService.js` now also rejects: URLs that decode to a script with no business being in an Israeli job URL (`hasSuspiciousUrlEncoding` — Cyrillic/CJK/Hiragana-Katakana/Hangul, or malformed percent-encoding), and per-domain "this is a listing page, not a posting" patterns (`looksLikeJobListingPage` — e.g. LinkedIn URLs must be `/jobs/view/<slug>-<numeric id>`, Indeed must be `/viewjob?jk=...`, AllJobs must carry a numeric `JobID=`, rejecting `SearchResultsGuest.aspx`). Unknown domains only get a couple of generic markers checked (`searchresults`, `-jobs-in-`) — this is a heuristic denylist, not a guarantee; a live HTTP check of the URL would be more reliable but adds network calls per candidate, deferred for now. `aggregatorName`/`aggregatorUrl` separately record where the posting was found (e.g. "LinkedIn") and that listing's own URL, which may differ from `url`; both are optional (a candidate missing them is still saved, just without source attribution).
- Dedup has two layers in `saveSearchResults`: exact `url` match (the DB `UNIQUE` constraint) catches the same link found twice; `isLikelyDuplicate` additionally catches the *same job under a different link* (e.g. LinkedIn vs. the company's own career page) by description similarity **alone** — word-overlap (Jaccard) of the two ad texts ≥0.5, with no company/title/location gating (an earlier version required those three to match first; simplified to description-only by explicit request). This means two postings with near-identical descriptions dedupe even if the company/title/location look unrelated (e.g. a recruiter re-listing the same client role under a different name) — the tradeoff is a (currently unmitigated) risk of merging two genuinely different roles that happen to reuse the same boilerplate description. Like URL dedup, this is checked against **all** postings in the DB, not scoped to the searched title — the same known limitation as URL dedup (two overlapping titles, e.g. "Product Manager"/"Senior Product Manager", can't both surface a posting once one has claimed it). A duplicate is silently skipped, never merged into the existing row — no cross-source tracking of "same job found via multiple aggregators" beyond keeping whichever `aggregatorName`/`aggregatorUrl` was saved first.
- Resume adaptation never edits a template in place: `resumeExtractionService.js` pulls plain text out of the template (`.docx` via `mammoth`, `.pdf` via `pdf-parse`, `.txt`/`.md` read directly), OpenAI adapts that text, and `resumeGenerationService.js` writes a brand-new document in the same format (`.docx` via `docx`, `.pdf` via `pdfkit`). The regenerated file is plain/unstyled — the original template's visual layout is not preserved, only its file format.
- "Never invent or drop content" (Story 4.2) is enforced via a **self-reported** check inside the single adaptation call: the model reports `originalPositionCount` and `retainedPositionCount`; `resumeAdaptationService.adaptResumeForPosting` treats `retainedPositionCount < originalPositionCount` as a generation failure (`UpstreamError`, retryable). This is a v1 heuristic, not a rigorous guarantee — revisit if it proves unreliable in practice.
- The resume template is `Resume.<format>` at the **repo root** and nothing else — `resumeTemplateService.getResumeTemplateInfo()` walks `RESUME_TEMPLATE_FORMATS` (`docx`, `pdf`, `txt`, `md`) and returns the first that exists, so `.docx` wins when several are present. It takes no `db` argument; there is no upload path and no stored copy. Every `Resume.*` at the root is gitignored — it's a personal file, never committed. Adapted resumes are written to `ADAPTED_RESUMES_DIR/posting-<id>.<format>`, one per posting, overwritten on regeneration.
- Tests must never see a real OpenAI key: `server/vitest.config.js` sets `env: { OPENAI_API_KEY: '' }`, because `config.js` loads the repo-root `.env` and a real key there would otherwise satisfy every "no key configured" test. Blank rather than unset — dotenv won't override a variable that's already present. Tests that *need* a key use `vi.stubEnv('OPENAI_API_KEY', 'sk-test…')` with `vi.unstubAllEnvs()` in `afterEach`; tests that need a template write a real `Resume.txt` at the repo root (via `resumeTemplatePathFor`) and delete it afterwards.
- File uploads (`POST /api/postings/:id/applied-cv`) use `multer` with in-memory storage — the route validates format/size in `appliedCvService.js`, not in Multer's own filter, so error messages stay consistent with the rest of the app's `ValidationError` handling.

## Playbook: adding an endpoint
1. Add/extend a function in the relevant `src/services/*.js` file — pure business logic + DB access, throwing `ValidationError`/`NotFoundError` as needed. Write its unit test first (`test/<service>.test.js`), using `createDb(':memory:')`.
2. Add a route in `src/routes/*.js` that calls the service inside a `try/catch` → `next(error)`. Write its Supertest test (`test/<routes>.test.js`).
3. Wire the router into `src/server.js` (import + `registerXRoutes(app, db)` call), **before** the `app.use(errorHandler)` line and before the static-serving block.
4. Run `npx vitest run` from `server/`.

## Playbook: disk-backed service tests

Services that write real files (`resumeAdaptationService.js`, `resumeGenerationService.js`, `appliedCvService.js`) still use `createDb(':memory:')` for the DB, but write small real files under `ADAPTED_RESUMES_DIR`/`APPLIED_CVS_DIR` (from `config.js`) — plus a throwaway `Resume.txt` at the repo root when a template is needed. Their tests clean up with `fs.rmSync(dir, { recursive: true, force: true })` in `afterEach` — there is no in-memory filesystem equivalent to `:memory:` for this app's scale, so tests share the real (small) local `server/data/` tree and are responsible for tidying up after themselves. File-level parallelism is disabled in `server/vitest.config.js` because these tests share real directories under `server/data/` — don't re-enable it without giving each test file its own isolated directory first.
